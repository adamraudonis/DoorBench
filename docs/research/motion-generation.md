# Motion generation for DoorBench

Research snapshot: 2026-09-05. Primary papers, official repositories, their source/configuration files, and provider license pages only. This was a source audit, not an installation or runtime benchmark. No body models, checkpoints, motion datasets, or external avatar assets were downloaded. The conclusions below are engineering recommendations; none of these methods has been evaluated on DoorBench here.

**Recommendation:** build a contact-aware reference system around DoorBench's actual articulation and an original, joint-limited character. Use a small library of original or explicitly cleared motion primitives for style, and constrained whole-body optimization for adaptation. OmniRetarget is the strongest implementation reference for the adaptation layer; CHOIS is a useful optional learned proposal generator after dependency rights are resolved. Retain a separate path for future physics-controlled execution. A visually attractive diffusion sample, a feasible pose sequence, and a dynamically successful door operation are three different results.

## Six strongest candidates

| Method | Demonstrated capability and relevance | Available implementation and practical cost | Rights and DoorBench limitation |
|---|---|---|---|
| **OmniRetarget / Holosoma** (ICRA 2026) | Interaction-mesh retargeting preserves relationships among body, objects, and terrain while constraining joint limits, penetration, and planted feet. Particularly useful for adapting an authored pull/step/reach primitive to many handle positions. [Paper](https://arxiv.org/html/2509.26633v1), [project](https://omniretarget.github.io/). | Public optimizer; no learned checkpoint required for retargeting. Custom input can be `(T,J,3)` world joint positions. Current implementation uses MuJoCo, CVXPY/Clarabel, NumPy, libigl and URDF tooling; Python ≥3.10. Separate setup supports macOS as well as Linux. Batch runner exists. No end-to-end DoorBench throughput measured. [Guide](https://github.com/amazon-far/holosoma/tree/bccd4d7451640a2800ddc77e469d911a84f91994/src/holosoma_retargeting). | Apache-2.0 code. The HF trajectory card says MIT and excludes LAFAN-derived trajectories for licensing reasons. Prefer original source motions and our own rig; do not assume all bundled demos/assets share the code license. Released examples focus on carrying/climbing, not articulated latch/door operation. Door component constraints and hand contact orientation need integration. [Dataset card](https://huggingface.co/datasets/omniretarget/OmniRetarget_Dataset). |
| **CHOIS** (ECCV 2024) | Joint human/object generation from text, initial state, geometry, and sparse object waypoints; sampling guidance improves hand/object and foot/floor contact. Scene-aware sequences use planned waypoints. Useful for body style and approach proposals. [Paper](https://arxiv.org/abs/2312.03913), [project](https://lijiaman.github.io/projects/chois/). | Training/inference code and checkpoint links are public. Tested stack: Ubuntu 20.04, Python 3.8, CUDA 11.3, PyTorch 1.11, PyTorch3D, BPS, human_body_prior. Demo window is 120 frames. README reports >1 hour initial BPS preprocessing and about 32 GB data/cache space; this is not training time. No reliable per-door latency/VRAM figure found. [Repository](https://github.com/lijiaman/chois_release). | MIT code; README requires separately obtained SMPL-X and processed OMOMO data. Separate checkpoint redistribution terms were not identified. A sparse rigid-object waypoint condition does not enforce DoorBench hinges, locks, linkage closure, or exact recorded body poses. Treat generation as a proposal and project onto authoritative door/contact constraints. |
| **OMOMO** (SIGGRAPH Asia 2023) | Given full object motion, first predicts hands, then full-body motion. Hand trajectories provide an explicit contact interface. A direct conceptual fit when DoorBench already supplies native body trajectories. Training capture covers approximately 10 hours and 15 objects. [Paper](https://arxiv.org/abs/2309.16237), [project](https://lijiaman.github.io/projects/omomo/). | Public code, data links, and two pretrained stages. Same older CUDA/PyTorch3D stack as CHOIS; 120-frame testing windows. It needs an adapter for DoorBench geometry, coordinates, and contacts. GPU runtime and minimum memory were not established in this audit. [Repository](https://github.com/lijiaman/omomo_release). | MIT code; SMPL-H/SMPL-X and dataset dependencies require separate rights. No explicit separate rights grant for downloadable weights/data was found in the inspected release text. Large-object manipulation does not demonstrate finger grasp, lock operation, narrow openings, or multi-link door mechanics. |
| **CLoSD / DiP** (ICLR 2025) | Text/joint-target diffusion planner coupled to an RL tracker with simulation feedback. Demonstrated navigation, striking, sitting, and getting up. Strong model for a later closed-loop controller. [Paper](https://arxiv.org/html/2410.03441v1). | Public code/checkpoints, Ubuntu 20.04/Python 3.8/Isaac Gym. README lists roughly 4 GB GPU memory for running and roughly 50 GB for training/evaluation. Paper's 11.4 ms figure is for a 40-frame DiP proposal, **not** complete simulated door execution. [Repository](https://github.com/GuyTevet/CLoSD). | MIT code, but first execution automatically downloads cached SMPL, AMASS, and HumanML3D dependencies. Do not run that bootstrap under the current no-uncleared-assets requirement. Targeting a wrist location is not a dexterous grip or door articulation constraint; a new environment and policy adaptation would be needed. |
| **InterMimic** (CVPR 2025) | Physics-based human/object imitation, correction, and retargeting; public G1 dexterous-hand demonstration. Most relevant when feasibility must include actual forces, contact, and balance. [Paper](https://arxiv.org/abs/2502.20390). | Public teacher/student training, sample teacher and student checkpoints; Isaac Gym and newer Isaac Lab inference. Recommended Lab combination is Isaac Sim 5.1.0 / Lab 2.3.1. Current high-fidelity training configuration uses 4,096 environments and four substeps. Multi-GPU scripts exist. No supported training-hours/minimum-VRAM promise found. [Repository](https://github.com/Sirui-Xu/InterMimic). | MIT code; repository explicitly separates third-party dataset/library terms. SMPL-X-derived humanoid and OMOMO/InterAct dependencies need provenance review. Existing released policies are not evidence of arbitrary DoorBench door manipulation. Higher integration and training cost than offline reference optimization. |
| **SK-HOI** (August 2026 preprint; project labels SIGGRAPH Asia 2026) | Explicitly handles multiple rigid parts and articulated assemblies with surface keypoints, a contact-distance field, and contact-guided body synthesis; accepts full object trajectories. Closest generative representation match to doors with moving leaves/operators. [Paper](https://arxiv.org/html/2608.03158v1), [project](https://www.ericpeng.site/project_websites/SK-HOI/). | Training/sampling code is public, but checkpoints and dataset preparation remain unchecked release items. CUDA 11.8 paths and external body dependencies appear in setup. Paper reports A6000 training and 4.21 minutes for body synthesis with contact optimization, plus 0.81 seconds for object/contact stages. At that reported sample cost, 1,000 serial samples imply roughly 70 hours; this extrapolation excludes training, retries, and rendering. [Repository](https://github.com/neu-vi/SK-HOI). | MIT code; weights unavailable at inspection. Uses ParaHome/OMOMO/HIMO/ARCTIC and SMPL-X fitting, each requiring independent rights review. Soft contact optimization and learned keypoints do not guarantee valid native joint mechanisms. Paper documents missed contact and body-fitting/foot-floating failures. Research watchlist, not a ready production dependency. |

## Relevant approaches not selected

- **InterGen** generates interactions between two people, rather than between a person and a door/scene mesh. Code and checkpoint download script exist, with a Python 3.8/CUDA environment. The README applies CC BY-NC-SA 4.0 to the work and separately prohibits dataset redistribution. It is a poor fit for DoorBench's permissive public dataset and required articulated contact. [Official repository](https://github.com/tr3e/InterGen), [paper](https://arxiv.org/abs/2304.05684).
- **PrimHOI** provides especially relevant contact primitives and an explicit door-opening example. Its high-level plan, contact-constrained key poses, object trajectories, and intermediate-motion refinement are useful architectural references. However, the official code repository at inspection contains only README and MIT LICENSE, with no executable implementation or weights. [Project](https://kairobo.github.io/PrimHOI/), [repository](https://github.com/Kairobo/PrimitiveHOI).
- **Human-X Interaction** releases its reaction diffusion planner, but the capture and physics tracker modules are still marked coming soon. Its demonstrated conditioning concerns another human's motion. [Official repository](https://github.com/humanx-interaction/Human-X-Interaction).

## Practical plan for this repository

1. **Keep mechanical truth authoritative.** Generate contact targets from each moving part's native pose, named operator/handle site, contact normal, and task phase. Include palm orientation, grip span, release events, and both-hand requirements. Do not infer contact solely from the benchmark's generalized-force action or a text description. Preserve source hashes and distinguish historical recordings from newly planned demonstrations.
2. **Separate task planning from style.** Define original primitives for approach, reach, lever/knob operation, push, pull with backward steps, sliding, two-handed wheel rotation, crouching, and overhead work. Include gazing before reaching, torso anticipation, relaxed free arm, planted support, controlled release, and follow-through. Adapt stance and handedness to free space and sweep direction. Style variants must satisfy the same contact plan.
3. **Solve a whole-body trajectory.** Use a rig with fixed lengths, joint orientations/limits, feet/toes, palms, and an adequate collision model. Optimize root placement, elbows, torso, and steps together; keep stance feet fixed during each support interval. Constrain body/door/frame/self collision, handle contact position/orientation, joint velocity, and temporal smoothness. OmniRetarget supplies useful objectives and solver structure. Its current self-collision option defaults off and its source accepts `OPTIMAL_INACCURATE`, so solver status alone must not be a pass certificate. A door adapter still needs explicit moving-component collision geometry.
4. **Validate the final sampled motion, including interpolation.** Record worst-frame reach/orientation residual, limit violation, penetration depth, stance-foot drift, root/limb speed and jerk, and door/body clearance. Use an explicit declared tolerance and physical collision mesh for each metric. Replan failures rather than stretching limbs or hiding residuals. Independent FK and scene checks should run after solving. For inaccessible hardware or a human-inappropriate passage, change the task/embodiment or report infeasibility; do not imply human traversal of every opening.
5. **Review style visually across all 1,000 doors.** Automated checks cannot establish convincing weight shifts, timing, or intent. Screen every clip and audit difficult examples at full resolution: low/overhead hardware, heavy wheels, reverse swing, two leaves, bifolds, hatches, narrow turnstiles, and powered doors. Store style review separately from kinematic and dynamic results.
6. **Add learned priors and physics later through explicit gates.** Pilot a rights-cleared CHOIS/OMOMO proposal on representative simple doors before scaling; preserve native articulation through optimization. Use InterMimic or a task-specific MuJoCo/Isaac controller if the requirement becomes physical humanoid execution. Quasi-static support checks can help reference quality but do not establish dynamic balance or available manipulation force.

Current `doorbench/reference/humanoid.py` provides a 16-joint position skeleton, two-bone IK, measured wrist residuals, and heuristic foot support. `record.py` explicitly says the doors are driven by generalized forces and the figure is kinematic. This is a useful interchange/provenance base, but lacks a full orientation/limit/collision representation. Extend a versioned motion schema with rig definition, local rotations, contact schedule, planned task, tolerances, and measured validation results; do not relabel existing 879 successful primary door recordings as 879 feasible humanoid performances.

## Release rights and verification scope

The published [SMPL-X model license](https://smpl-x.is.tue.mpg.de/modellicense.html) restricts use to specified non-commercial purposes and prohibits redistribution of the model/software. The [AMASS license](https://amass.is.tue.mpg.de/license.html) also restricts use and distribution. A code repository's MIT badge, or retargeting a motion onto another rig, is insufficient evidence that dependency assets, checkpoints, source motions, or derived artifacts can be republished under DoorBench's license. This audit did not determine blanket rights for generated outputs. Use original rig/assets and original motion data for the release path, and require explicit provenance/terms before adopting other content.

Holosoma's current package configuration explicitly includes bundled motion/weight files and robot meshes. A normal package install may therefore bring additional assets even when only the optimizer is desired. Inspect a source-only subset and its notices before adoption; do not automatically execute its data demo or install scripts. No external bootstrap was executed during this review.
